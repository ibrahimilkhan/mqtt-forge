# The broker lab

Four brokers, three vendors, every transport and every MQTT version MQTTForge claims to speak.
For pointing the console at something real by hand — the automated tests start their own
containers and generate their own certificates, and do not touch any of this.

```
./up.sh      # generates certificates on first run, then prints the table below
./down.sh
```

## The parts worth knowing

**Mosquitto 1.5, not 1.6.** MQTT 5 arrived in mosquitto 1.6.0, so the last of the 1.x line
answers a v5 CONNECT perfectly happily. 1.5 is the version that actually refuses it, which is
what the console's Auto has to notice and step down from.

**Two certificates are broken on purpose.** Ports 28885 and 28886 serve an expired certificate
and one issued for a name nothing is dialled by. Both look like "untrusted" by the time the
exception surfaces, and telling them apart is the console's job.

**The mutual-TLS listener refuses a connection with no client certificate**, which is what AWS
IoT Core and most locked-down industrial brokers do. `certs/stranger.pfx` is a well-formed
certificate signed by nobody it knows, for the other half of that case.

**The certificates are throwaways** regenerated by `make-certs.sh` into `certs/`, which is not
tracked — a CA key in a repository is a CA key anybody can sign with. Delete the directory to
issue a fresh set. They are made inside a container rather than with the host's `openssl`,
because macOS ships LibreSSL and it refuses half of what they take.
